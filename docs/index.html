Episode triage

A robot fleet produces more failures than a small team can look at. The costly mistake is retraining the policy on a failure that was really a frozen camera or a joint that didn't do what it was told. This tool reads the logs and checks those cheap layers first. A failure goes to training only when the cameras were fresh and the joints followed their commands.

Independent project by Avi Desai. Not affiliated with Weave Robotics. Data: the LeRobot community dataset (Apache 2.0), 1,427 SO 100 and SO 101 arms built and calibrated by different people. Code and every number below: github.com/avidesai/episode-triage.

Across 1,427 arms, that check found joint or calibration faults on about 1 in 7 arms and frozen cameras in about 1 in 14 recordings. It also proved my own prediction wrong: nearly every stall was really the operator pausing.

  • Frozen cameras don't show up in the timestamps. LeRobot writes each timestamp as frame number divided by frame rate, so all 48,208 recordings have a perfect clock. Comparing each camera's picture with the arm's motion found 58 of 809 sampled recordings, on 43 arms, where a camera stopped updating while the arm moved.
  • Joint faults are common, and mostly calibration. 197 arms have at least one: the follower sits off its leader at rest (92 arms), the two arms were calibrated over different ranges (36), bad motor readings (34), or a reading that wraps from +180 to -180 degrees so the follower spins the long way round.
  • My stall prediction was wrong. I wrote down beforehand that at least a quarter of stalls would start with a camera or joint fault. It was 4 of 355. In this data the check mostly confirms that a stall is a real task failure, and those 322 go to training with the evidence attached.

The ladder

Every problem ends up on one of five rungs. The rules run in a fixed order and the first match wins. The first rule checks the data itself: if a camera wasn't checked or the data is broken, the problem goes to a person with a one line reason, so nothing reaches training on a guess. How late each camera runs

For each arm, the delay at which a camera's picture changes line up best with the arm's motion. Most of the 395 cameras run 0 to 2 frames behind the joints, which is normal for a USB camera. 46 cameras on 40 arms run 3 frames (100 ms) or more behind, up to 5. Data merged from those arms disagrees about when the gripper saw the object. 4 cameras appear to run ahead of the joints, which can't happen, so the estimate is probably wrong for them.

Does it catch what it claims to?

I injected known faults into real recordings and checked whether the tool caught them. Video faults were compressed again with LeRobot's own settings, so a frozen picture reaches the tool the same way a real one would. One threshold was tuned on data (how little a picture can change and still count as frozen), set on 20 arms. It was then frozen and tested on 40 different arms. Caught, low confidence: the tool found the frozen picture, but that camera barely shows the arm moving, so it logs the finding and doesn't act on it. This guard stops a camera that can't see the arm from being blamed for a stall, and here it costs more than half the catches. Skipped: the recording had fewer than two pauses, so a resting offset couldn't be measured. False extras: anything else the injected fault set off. A camera delayed by 3 frames was measured within 1 frame of that on 37 of 38 recordings. Injected faults test the rules against a known answer; they don't show that natural faults look the same.

What a robot should record so this stops being inference

  • Capture time per frame, from the camera or a hardware trigger, next to the loop time. With those, stale frames and camera lag become a subtraction instead of a cross check.
  • Real loop period. A slow loop is only a log line today; nothing about it reaches the data.
  • Per motor load, temperature, voltage and status byte. The servos on these arms report all four over the same bus and none is recorded by default. They would turn "not following" into "unloaded on overload" or "brownout".
  • The goal actually sent after any clipping, beside the leader or policy command.
  • Every takeover with the progress score and subsystem health at that moment. Each one is a failure someone has already labeled.

The flight recorder in recorder/ is written to log the first four on an SO 101 as a sidecar to a normal LeRobot dataset, with a scheduled fault injector and a run sheet. It hasn't been run on hardware yet; recording that bench set is the next step, and the report adds its table when it exists.

What's wrong with it

  • Frozen cameras and camera delay are inferred by comparing pictures with joint motion, because the data has no real clock. A camera moving over a blank surface can look frozen; those cases get low confidence and stay out of the counts.
  • Almost all of this data is people teleoperating, so "send to training" here means a task level stall or miss by the operator, not a learned policy failing.
  • Joint positions alone can't always tell a grasp on thin cloth from closing on nothing.
  • Each dataset counts as one arm. Some people recorded several datasets on the same arm, so arm counts are an upper bound.
  • The video checks ran on a random sample (298 arms, up to 3 recordings each), not every recording.
  • Every validation number on this page comes from faults injected in software. None comes from a physical fault on a real arm yet, and injected faults are cleaner than natural ones.
