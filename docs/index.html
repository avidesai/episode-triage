How it decides

Three layers of checks run on every run, cheapest evidence first: did the cameras deliver fresh pictures, did the joints do what they were told, and only then, did the task progress. For each failure, the earliest camera or joint problem that began before it is the cause; anything that began after is context. Then ordered rules decide the rung, first match wins. Every threshold is a fraction of a joint's range measured from that arm's own data, so the same rule runs on arms recorded in different units.

The ladder

Rules run in this order; the first that matches wins. Counts are incidents in the sampled runs (all layers checked) and in all runs (joints only). Click a count to see those incidents.

What's wrong with it

  • Frozen cameras and camera delay are inferred by comparing pictures with joint motion, because this data has no real capture clock. A camera moving over a blank surface can look frozen; those cases get low confidence and never drive a verdict, which costs recall.
  • Almost all of the demo data is people teleoperating, so "send to training" here means a task level stall or miss by the operator, not a learned policy failing.
  • Joint positions alone can't always tell a grasp on thin cloth from closing on nothing, and can't tell a joint pushing against the world from a dead one. Those go to a person.
  • Each dataset counts as one arm; some people recorded several datasets on one arm, so arm counts are an upper bound.
  • Camera checks ran on a random sample of arms, not every run.
  • Validation so far is faults injected in software into real runs. The live monitor and the recorder exist so the same checks can be scored against faults caused on purpose on a physical arm.

What a robot should record so this stops being inference

  • Capture time per frame from the camera or a hardware trigger, next to the loop time. Frozen frames and camera lag then become a subtraction instead of a cross check.
  • Real loop period. A slow loop is only a log line today.
  • Per motor load, temperature, voltage and status. These servos report all four over the same bus and none is recorded by default. They turn "not following" into "unloaded on overload" or "brownout".
  • The goal actually sent after any clipping, beside the command.
  • Every takeover with the progress score and subsystem health at that moment. Each one is a failure someone has already labeled.

Running it on your own logs

Everything downstream of the reader works on one object, Episode: commanded and measured joint positions, frame rate, which columns are grippers, and a way to get each camera's frames. A new log format needs one file that produces that object; the checks, the cause ordering, the ladder, the inbox and the live monitor run unchanged. episode_triage/readers_template.py in the repo is a starting point. Logs never leave your machine: the tool runs locally and this page is static.
